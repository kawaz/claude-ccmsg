# エンドポイント自己識別プロトコル

- 起草: kawaz (2026-09-07)。[mesh-peer-auth.md](./mesh-peer-auth.md) の `self` を確定する手続き

mesh ノードが起動時に、共有のエンドポイント一覧のうちどれが自分かを確定する手続き。

---

## 1. 目的

自分の識別子を管理対象にしない。[mesh-peer-auth.md](./mesh-peer-auth.md) §1 の後段 (管理するものを増やさない) を、自分の識別子についても満たす。

自分の URL を設定に書くと、ノードごとに設定が異なることになり、mesh 全体へ同一の設定を配れなくなる。差分管理という管理対象が増える。

あわせて、一覧に書かれた各エンドポイントの到達性と記述の正しさ (typo など) を起動時点で検証したい。設定ミスが実行時ではなく起動時に露見するようにする。

## 2. 解きたい問題

自分がどのエンドポイントとして外から見えているかを、ノード自身が知る手段がない。

リスニングソケットからは、どの URL 経由で到達されたかが分からない。Host ヘッダは接続元が指定する値であり、前段に LB を挟めばパスも書き換わる。いずれも自己識別の根拠にならない。

一方で [mesh-peer-auth.md](./mesh-peer-auth.md) の `aud` 検証には、自分の URL が確定している必要がある。認証側が求めるのは起動時までに確定していることだけで、確定手段は問わない。

## 3. 前提条件

| # | 条件 | 満たさない場合 |
|---|---|---|
| Q1 | 全ノードが同一のエンドポイント一覧 (`peers`) を持つ | 一覧に差分が生じ、§1 の目的が失われる |
| Q2 | 一覧に自分自身のエンドポイントが含まれる | 一致 0 個で起動失敗 (§5.3) |
| Q3 | 起動時、一覧の各エンドポイントへ到達できる | 同上 (ccmsg での適用: 片方の PC が寝ている運用が常態なので、到達しない peer は一致数の計算から外して続行し、起動失敗は一致 0 / 2 個以上に限る。§4.2 の性質は「自分宛は必ず届く」にしか依存しないので崩れない。統括判断 DV-Q11、[daemon-v2.md](./daemon-v2.md)) |
| Q4 | probe を TLS 上で送り、サーバ証明書を検証する | `token` が経路上で漏れ、誤認を誘導される (§4) |

## 4. 信頼モデル

信頼の根は二つある。`token` の推測不能性と、TLS による経路の保護である。

`token` は送信先ごとに異なる 128bit のランダム値で、送信側だけが対応表を持つ。その値を知っていること自体が、それを自分が送ったことの証明になる。

### 4.1 TLS が必要な理由

`token` は推測できないが、傍受はされうる。`token_i` を経路上で盗んだ攻撃者がそれを送信元自身へ送り返すと、送信元は「`token_i` が届いた」と解釈し、自分を `peer_i` だと誤認する。

したがって probe は TLS 上で送り、サーバ証明書を検証しなければならない (Q4)。これにより `token_i` は `peer_i` にしか到達せず、経路上の第三者は傍受も注入もできない。

`token` は TLS 内では平文でよい。追加の暗号化も署名も要らない。秘匿すべきは対応表と TLS 経路であって、`token` 自体の表現ではない。

### 4.2 悪意ある正規ピアの扱い

`peer_i` 自身が受け取った `token_i` を送信元へ送り返せば、上と同じ誤認を狙える。TLS では防げない。正規のピアなので証明書は正当である。

これは §5.3 の一致数判定で不成立に終わる。送信元は自分自身にも probe を送っており、その 1 通は必ず自分に届く。攻撃者は自分宛の probe に介入できないため、一致は必ず 2 個以上になり、起動失敗となる。誤認ではなく可用性の低下に落ちる。

送信元が「自分自身にも probe を送る」ことは、この性質のために必須である。`peers` から自分を除いて送る最適化をしてはならない。

## 5. プロトコル

### 5.1 手順

```
起動時:
  1. 各 peer_i に対し token_i = random(128bit) を生成し、対応表に記録
  2. peer_i へ probe を送信 (すべて並行でよい)
       probe: { ver, token: token_i }
  3. 自分のハンドラに届いた probe の token を対応表と照合
  4. 一致した i の URL を self とする
  5. 全リクエストの完了後、対応表を破棄
```

送信も受信も同一プロセスで行う。自分宛の 1 通は自分に届き、他は他ノードに届く。他ノードに届いた probe は、そのノードの対応表に無いので照合が外れる。

`peers` に含まれる全エンドポイントへ送る。自分宛を除外してはならない (§4.2)。

`ver` は probe のフォーマットを将来変更するための逃げ道であり、[mesh-peer-auth.md](./mesh-peer-auth.md) の `ver` とは独立に採番する。未知の `ver` の probe は無視してよい (照合は送信側が行うため、受信側が解釈できなくても送信側の判定には影響しない)。

probe を受けたノードは、それが自分宛かどうかに関わらず応答してよい。照合は送信側が行う。probe の受理に認証は不要である。

### 5.2 信頼の連鎖

初期状態で信頼しているのは、設定のエンドポイント一覧と CA の 2 つだけである。ここから `self` の確定までを追う。

1. 設定への信頼により、`peers` の各 URL が正当なピアであることを信頼する
2. 各 URL の TLS により、その URL への送信経路を信頼する
3. 経路への信頼により、`token_i` が `peer_i` にのみ届いたことを信頼する
4. 自分に届いた `token` が対応表にあることにより、その `token` は自分が送ったものだと信頼する
5. 送信先が `peer_i` だったことにより、自分が `peer_i` であることを信頼する ★

3 が TLS に依存する箇所であり、ここが崩れると 4 以降が成立しない (§4.1)。5 は一致が 1 個のときのみ成立し、2 個以上なら送信先を一意に決められないため確定しない (§5.3)。

### 5.3 判定

| 一致数 | 判定 |
|---|---|
| 1 | `self` が確定。正常 |
| 0 | 起動失敗 |
| 2 以上 | 起動失敗 |

0 個は、自分が `peers` に含まれていない (Q2 違反)、自分宛の URL が誤っている、または外部から自分へ到達できない、のいずれか。

2 個以上は、同一ホストが別名で複数登録されている、DNS が複数の名前を同じ宛先へ向けている、といった状況。どちらを正式な名前とすべきか決められないため、握りつぶしてはならない。認証側の `aud` 検証が後から不定に失敗する原因になる。

いずれも設定ミスとして起動時に落とす。実行時に持ち越さない。

### 5.4 トランスポート

HTTPS でも wss でもよい。やることは同じであり、規定しない。

既存のリスナーに相乗りさせる場合、probe を認証済みメッセージと区別できるようにすること。[mesh-peer-auth.md](./mesh-peer-auth.md) の §5.8 は ack 前のメッセージを受けた接続を close すると規定しているため、probe をそのハンドシェイクと同じ経路に流すと、自分の probe で自分の接続が切られる。専用のパス、あるいは接続確立直後に判別できるメッセージ型として分離する。

### 5.5 実行タイミング

起動時に一度だけ。以降 `self` は固定する。

エンドポイント一覧が変更された場合は再実行する。結果によって処置が決まる。

- `self` が変わっていなければ、何もしない
- `self` が変わっていれば、確立済みの接続をすべて張り直す。相手が検証した `aud` の前提が変わっているため

一覧から削除されたピアへの接続は、`self` の変化とは無関係に close する。

### 5.6 推奨値

| 項目 | 値 | 根拠 |
|---|---|---|
| `token` 長 | 128bit 以上 | 推測不能であればよい |
| 送信 | 全 peer へ並行 | 逐次にする理由がない。ノード数に比例して起動が遅くなる |
| タイムアウト | 数秒 | 到達しないピアがあれば設定ミスとして落とす。長く待つ意味がない |

## 6. 適用範囲外

- `peers` の継続的な到達性監視。起動時点のスナップショットしか取らない。死活監視は認証プロトコル側のハートビートが担う
- 自分の URL が外部からどう見えるかの一般的な解決。NAT や複数 IP を持つ環境で確定できるのは「`peers` のうち自分に到達したもの」であり、それ以上ではない
- probe 送信元の認証。probe は認証前に処理される。受理しても状態を持たないため、認証を要求しない
- TLS を張らない経路での動作。Q4 を満たさない構成は対象外 (§4.1)

## 7. テスト

### 7.1 判定

- 一致 1 個 → `self` が確定すること
- 一致 0 個 (自分を `peers` から外す) → 起動失敗
- 一致 2 個以上 (同一ノードを別名で 2 つ登録) → 起動失敗

### 7.2 トークンの照合

- 他ノード宛の `token` を自分のハンドラへ注入しても、照合が外れること
- ランダムな `token` を注入しても照合が外れること
- 自分宛の `token` を第三者経由で送り返されたとき、一致 2 個で起動失敗すること (§4.2)
- 自分宛の probe を送信対象から除外していないこと (§4.2 の性質が成立する条件)

### 7.3 状態の非残存

- 全リクエスト完了後に対応表が破棄されていること
- 確定後、`self` 以外の探索状態が残らないこと

### 7.4 境界ケース

- probe が認証プロトコルのハンドシェイクと混線しないこと (§5.4)。probe 送信によって自分のハンドシェイク接続が close されないこと
- 到達できないピアが一覧にある場合、タイムアウトで起動失敗すること

## 8. 既知の同等物

近いのは STUN の考え方 (自分の外形的なアドレスを外部への問い合わせで知る) だが、STUN が NAT 越しの IP:port を得るのに対し、本プロトコルは既知の候補集合から自分を選ぶ点が異なる。候補が有限で既知であるため、探索ではなく照合で済む。

## 9. 検討し、採用しなかった選択肢

| 方式 | 不採用の理由 |
|---|---|
| `self` の設定への直書き | ノードごとに設定が異なり、同一設定の配布ができなくなる。§1 そのものに反する |
| Host ヘッダ / リクエストパスからの逆引き | Host は接続元が指定する値であり、前段 LB でパスも書き換わる。自己識別の根拠にならない (§2) |
| probe への署名 | 傍受された probe の送り返しは署名でも防げず、TLS が要る点も変わらない (§4.1)。鍵の生成・配布・検証というコードパスが増えるだけで保証は増えない |
| 自分宛 probe の送信省略 | 一致 2 個以上で失敗する性質が成立しなくなり、悪意ある正規ピアによる誤認を許す (§4.2) |
| 全ピア共通の単一 `token` | どのエンドポイント経由で届いたかが判別できず、自己識別にならない |
| 到達性の継続監視を兼ねる | 定期実行になり、頻度と失敗時の扱いという設計が増える。死活監視はハートビートの役割 (§6) |
| 一致 2 個以上での自動選択 (先着優先など) | どちらが正式な名前かはプロトコルからは決められない。`aud` 検証が後から不定に失敗する (§5.3) |
