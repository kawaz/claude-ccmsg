# 画面内検索のハイライト (CSS Custom Highlight) の重さ: live な Range の登録数と DOM 変更の関係

- Date: 2026-11-12
- 対象: ccmsg v0.264.0 の webui の画面内検索 (`rendered-text-search.ts` / `useInViewSearch.ts`)、playwright-cli 0.1.22 の Chromium 157 (headless) と WebKit (headless、UA は Safari 26.6 相当)
- 動機: issue `2026-11-10-in-view-search-live-range-webkit` の「一致が多い時に live な Range を CSS.highlights に登録していると WebKit が重くなる」という疑いを計測で確かめる
- 実 Safari は自動で動かしていない (下の「実 Safari」)

## 判明した事実

### 検索のハイライト (本題)

- WebKit では、live な Range を Highlight に登録していると、文書のどこで DOM が変わっても次のフレームの描画が登録数に比例して遅れる。リポの外の実験ページでは 1000 個あたり約 28ms で、500〜12000 個の範囲でほぼ直線 (12000 個で +334ms)。この形のページでは超線形にはならなかった
- WebKit で同じ数の live な Range を作って登録しないだけなら遅れは出ない。遅れは「live であること」と「Highlight に登録していること」が揃った時に出る
- WebKit で StaticRange に替えると、ハイライトのある箱の外の DOM 変更と、ハイライトのある文字の書き換えでは遅れが消える。ハイライトのある箱に子を足す変更 (TL の push と同じ形) では、StaticRange でも live と同じだけ遅れる
- Chromium では live / static / 登録なしのどれでも、12000 個まで遅れは出ない
- 実アプリ (1700 本文の TL、WebKit) で一致 5000 個の時に live な登録が足している時間 (登録なしとの差と比) は、TL の外の DOM 変更 1 回で +115ms (34 → 149ms、4.4 倍)、push 1 回で +198ms (1262 → 1460ms、1.16 倍)、↓ 1 回で +308ms (1069 → 1377ms、1.29 倍)、2 文字目の打鍵で +187ms (1054 → 1241ms、1.18 倍)。一致 1000 個では DOM 変更 1 回で +26ms (1.8 倍)、push・↓・打鍵では +20〜116ms (1.02〜1.11 倍)。スクロールは一致の数によらず中央値で 1〜3 フレーム (最大 133ms)
- 同じ実アプリで StaticRange に替えても、push は 1430ms で live の 1460ms と変わらない。TL の外の DOM 変更は 149 → 32ms に減る
- 比で小さく見えるのは、どの操作も検索と関係しない基準の時間が大きいから (下の「TL の基準の重さ」)。WebKit では一致 0 個でも push 1 回が約 1.2 秒、打鍵 1 回が約 1.0 秒、検索語の 1 文字目と空にする打鍵が約 2.1 秒かかる (一致 5000 個ではこの 2 つが 3〜5 秒)。Chromium では検索なしでも push 1 回が 3.3〜4 秒、TL の外の DOM 変更 1 回で同期 layout が 300〜380ms、打鍵 1 回が約 3.5 秒かかる。どちらもハイライトの登録をやめても (下の「登録なし」) 変わらない

### TL の基準の重さ (検索と関係しない)

issue `2026-11-05-timeline-push-cost-after-older` (読み切った TL では push ごとに重い) と同じ現象の材料として残す。

- この fixture の 1700 本文は、TL を普通に開いた最初の読み込みで全部描かれる。transcript が約 970KB で 1 回目の tail read (1 MiB) に収まり、先頭から読まれる。「過去分を上に読み込む」は使っていない。本文がどれも境界行 (吹き出し) なので fold に入らず、全部が DOM に載る。普段のセッションのように tool の呼び出しが fold に入る形より、同じバイト数で DOM に載る行が多い
- 同じ形の fixture で本文の数を変えた比較 (検索なし、push は 5 回の中央値、DOM 変更は TL の外の div への変更で同期 layout の時間)

| 本文 | 要素 | Chromium push | Chromium DOM 変更の layout | WebKit push | WebKit DOM 変更の layout |
|---|---|---|---|---|---|
| 200 | 約 3,400 | 48ms | 1ms | 71ms | 2ms |
| 600 | 約 10,000 | 194ms | 16ms | 231ms | 3ms |
| 1700 | 約 28,000 | 3,700〜5,600ms | 335ms | 1,253ms | 3ms |

- どちらのエンジンでも push は本文の数に対して超線形に伸びる (600 → 1700 で要素は 2.8 倍、push は Chromium で 20 倍以上、WebKit で 5.4 倍)
- Chromium の内訳 (devtools.timeline の trace、本文 1700、検索なし): push 1 回 (settle 3,037ms) のうち 2,852ms が 1 回の Layout。style の再計算は 0.5ms (60 要素)、paint は 2ms、JS の呼び出しは合計 5ms。Layout は dirty な object 58 個に対して、文書全体の 39,354 個の layout object をやり直していた (partial ではなく、layout の根は文書の 1 段目)。TL の外の div の変更でも同じで、dirty 5〜6 個に対して 39,305 個を 260ms かけてやり直した
- その 2,852ms の Layout は、JS の呼び出し (FunctionCall、rAF の callback) の中ではなく描画の段で走っていた。issue の元の計測にある `useStickToBottom` の `scrollHeight` の読みによる強制 layout は、この trace では大きく出ていない
- WebKit では、TL の外の DOM 変更の layout は本文 1700 でも 3ms で、Chromium のような全体のやり直しは見えない。push では、新しい行が DOM に入るのはメッセージを読んでから約 175ms 後で、次のフレームはそれから約 1.03 秒後だった。push の間に layout を強いる読み (`scrollHeight` 等) にかかった時間は 5 回中 4 回が 1〜2ms、1 回が 669ms。残りの約 1 秒が JS か描画かは分けていない (WebKit に LoAF が無い)
- TL の行には `content-visibility` も containment も当たっていない (`app.css` で `content-visibility` は 0 か所、`contain:` も 0 か所。`container-type` は TL の外のセッション一覧とキャッシュの輪の 2 か所だけ)。TL の箱 `.timeline-view` は `overflow-y: auto` の flex の列、行を並べる `.tl-lines` も flex の列で、どちらにも layout の境界になる指定は無い。computed style でも両エンジンとも、`.timeline-view` / `.tl-lines` / その子 (行) / 吹き出しの `content-visibility` は `visible`、`contain` は `none` (行と吹き出しも `display: flex`)

## 実用的な示唆 / ベストプラクティス

- WebKit で遅れを決めるのは「登録している live な Range の数」なので、登録を表示範囲の分だけに絞れば遅れはその数に比例して減る。StaticRange への置き換えだけでは、TL の push (箱への子の追加) の遅れは減らない
- 今の TL の重さの大半は検索のハイライト以外にある。検索を直しても push・打鍵の 1〜4 秒は残る。Chromium では、行が増えると DOM の変更 1 回ごとに文書全体の layout がやり直され、本文の数に対して超線形に伸びることまで分かった。どの CSS の組み合わせが全体のやり直しと超線形を生んでいるか、WebKit の約 1 秒が何かは未特定
- 検索の上乗せは、差 (ms) と比の両方で見る。基準が 1 秒台の操作では、0.1〜0.3 秒の上乗せが 1.1〜1.3 倍にしか見えない
- 実 Safari での確認は、下の計測片を TL で一致の多い検索中と検索なしで 1 回ずつ実行すれば足りる

## 方法

### fixture と隔離 daemon

- 隔離 daemon (作業コピーの `packages/daemon/src/index.ts --foreground`、`HOME` / `TMPDIR` / `CCMSG_STATE_DIR` / `CCMSG_CONFIG_DIR` / `CCMSG_DATA_DIR` を一時ディレクトリ、`CCMSG_CLAUDE_CONFIG_DIRS` に試験用の config home だけ)。試験用の config home に `sleep` の pid の `sessions/<pid>.json` と transcript を置いた
- transcript は user と assistant の本文を交互に 1700 行 (約 970KB、1 回の tail read に収まる)。どれも境界行なので fold に入らず、1700 個の unit が全部 mount される。本文の語は k / q / w / v / z / x / j / y を含まない語だけで作り、検索語をその文字だけで作った: `jy` (0 個)、`kq` (100 個)、`wv` (1000 個)、`zx` (5000 個)。検索語の 1 文字目だけでも一致の数が変わらない
- push は hooks module の代わりに、試験用の sid として hello して run を名乗る小さなスクリプトが、transcript に user と assistant を 1 行ずつ足して `transcript_push` を送る (webui には `ev:"transcript"` が届く)
- 条件ごとに fixture を 1700 行に戻し、daemon と送り手を起こし直して TL を開き直した (push で TL が伸びると値が伸びるため。最初の Chromium の通しでは戻さずに測り、1776 → 1874 本文の間で push の値が TL の長さに沿って伸びた)

### 操作と測るもの

- 操作
  - push: 送り手を叩いて 2 行を足す。t0 はページが WebSocket の `ev:"transcript"` を読んだ時刻
  - スクロール: TL の箱の `scrollTop` を ±1500px
  - ↓: 件数の横の ↓ ボタンを `click()`
  - 打鍵: 検索欄の値を 1 文字ずつ変えて `input` を送る。空 → 1 文字目 (0 → N 個) → 2 文字目 (N → N) → Backspace (N → N) → 空 (N → 0)
  - TL の外の DOM 変更: body に fixed の div を置き、子を 1 つ足して文字を書き換える (アプリのコードは走らない)
- 測るもの
  - settle: t0 から、フレームの間隔が 25ms 未満で 6 回続いた最初のフレームまで (rAF の時刻)。その間の最大のフレーム間隔 (maxGap) も取った
  - Chromium だけ Long Animation Frame (LoAF) で、フレームのうち描画 (renderStart 以降) とそれより前 (script) を分けた。WebKit は LoAF を持たないので分けられない
  - TL の外の DOM 変更は、変更の JS の時間と、`offsetHeight` で強制した同期 layout の時間も取った
- 登録の方式: `HighlightRegistry.prototype.set` をページの中で差し替え、アプリが作った Highlight を (a) そのまま登録 (live、今の実装)、(b) 同じ境界の StaticRange で作り直して登録 (static)、(c) 登録しない (登録なし) の 3 通りにした。アプリのコードは書き換えていないので、(b) (c) でもアプリは live な Range を作って持っている。WebKit は `CSS.highlights` のインスタンスへの代入を黙って無視するので prototype で差し替えた
- 1 条件 7 回 (Chromium の測り直しは 5 回)。値は中央値 (最小-最大)、単位は ms。計測中に `bun test` は走っていなかった (各条件の前に確認)

### 切り分けの実験ページ

- 一時ディレクトリの HTML を localhost で配った。角丸と背景のある段落 1700 個 (各 30 語) と、`::highlight(h)` の背景色
- 条件: Range なし / live な Range を N 個作って保持するが登録しない / live を N 個登録 / StaticRange を N 個登録 (各 5 文字、段落に順に散らす)
- 操作: 箱の外の fixed の div を書き換える (outside) / ハイライトのある箱の末尾に段落を足す (append) / 先頭の段落の文字の先頭に挿入する (editText、その段落の Range がずれる) / スクロール
- 測るもの: 変更の JS、強制した同期 layout、変更から 2 回目の rAF まで (toFrame)。何もしない時の toFrame は 2 フレームの約 33ms

Chromium では差が負になっている。測った順 (検索なし → 一致 0 個 → live → static → 登録なし) に値が伸びており、同じブラウザのプロセスを使い続けたことによる伸びが、方式の差より大きい。登録をやめて下がる様子は無い。

## 実 Safari

- この Mac の Safari は 26.5.2 (`safaridriver --version`)。`com.apple.Safari` の設定に `AllowRemoteAutomation` は無く、リモート自動化は有効になっていないと読める。`safaridriver --enable` は設定を変えるので実行していない。有効にしても WebDriver のセッションは Safari の自動化ウィンドウを前面に開くので、画面を使っている人のフォーカスを奪う
- 人の手で確かめるなら次で足りる (Web インスペクタのコンソールを使うので、Safari の設定で Web 開発者用の機能を表示している必要がある)
  1. Safari で webui を開き、本文の多いセッションの TL を開く
  2. 🔍 に一致が数千個になる語を入れる (件数の表示は unit の数なので、目安は件数 M が数百以上)
  3. Web インスペクタのコンソールに下の計測片を貼って実行し、表示された `highlights` と `median` を控える
  4. 🔍 を空にして、もう一度実行する
- headless の WebKit の fixture (一致 5000 個) では `highlights=5003 median=116ms`、検索なしで `highlights=0 median=33ms` だった。実 Safari で同じ程度なら、この findings の WebKit の表がそのまま実 Safari に当てはまると見てよい

```js
(async () => {
  const raf = () => new Promise((r) => requestAnimationFrame(r));
  const box = document.body.appendChild(document.createElement("div"));
  box.style.cssText = "position:fixed;left:0;bottom:0;font-size:1px";
  const rs = [];
  for (let i = 0; i < 9; i++) {
    await raf(); await raf();
    const t0 = performance.now();
    box.textContent = "t" + i;
    await raf(); await raf();
    rs.push(performance.now() - t0);
  }
  box.remove();
  rs.sort((a, b) => a - b);
  const n = [...CSS.highlights.values()].reduce((a, h) => a + h.size, 0);
  return `highlights=${n} median=${Math.round(rs[4])}ms min=${Math.round(rs[0])} max=${Math.round(rs[8])}`;
})()
```

## 分からなかったこと

- 実 Safari での値 (上の手順で人の手が要る)
- WebKit で一致 0 個でも push 約 1.2 秒・打鍵約 1.0 秒かかる内訳。push では新しい行が DOM に入った後、次のフレームまでの約 1 秒だと分かったが、JS か描画かは分けていない (WebKit に LoAF が無く、プロファイラも使っていない)
- Chromium の TL で、dirty が数十個の変更でも文書全体 (約 3.9 万 object) の layout がやり直され、本文の数に対して超線形になる理由 (flex の列の入れ子と containment が無いことが関わると見るが、CSS を変えて試していない)
- Chromium の trace で、強制 layout の呼び元を stack で取っていない (2,852ms の Layout が JS の呼び出しの外だったことだけを見た)
- 編集モードの PoC で見えた超線形が、この実験ページで出なかった理由
- この fixture は 1700 個の本文の吹き出しが全部 mount される形で、tool の呼び出しが fold に入る普段のセッションより mount される unit が多い。普段のセッションで mount される unit の数と、そこでの値は測っていない
- headless の Chromium の値が headed (GPU あり) の Chrome でも同じかは測っていない (layout は main thread なので同じ桁と見込むが未検証)
