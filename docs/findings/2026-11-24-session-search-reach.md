# Session Search が期間の中をどこまで読めるか (2026-11-24)

## 判明した事実

- 1 回の検索で読む量の上限 256MB では、既定の 5 日でも期間の中の transcript を読み切れない (5 日 63%、30 日 27%、60 日 20%、365 日 5%)
- 上限を外して期間の中を全部読むと、全部読む検索 (当たらない語) で 5 日 約 1.1 秒、30 日 約 2.3 秒、60 日 約 3.2 秒、90 日 約 4.0 秒、365 日 約 18 秒かかる (270〜420MB/秒)
- 1 回目と 2 回目で速さが変わらない。律速は CPU で、そのうち大半は大小区別なしの prefilter が行ごとに `toLowerCase()` した文字列を作ること。同じ行群で `toLowerCase()` + `includes` は約 490 Mchar/秒、大小を畳む正規表現 (`iu`) の `test` は約 4,400 Mchar/秒、大小区別ありの `includes` は約 7,000 Mchar/秒
- 大小区別ありの検索 (prefilter で小文字化しない) では、同じ全部読む検索が 60 日 約 1.2 秒、365 日 約 8.1 秒
- 語の無い検索 (一覧) は各ファイルの先頭で止まるが、最初の読みが 4MB 単位なので 1 ファイル最大 4MB 読む (365 日で 3.2GB 読んで約 6.7 秒)
- 走査は `projects/<project>/*.jsonl` だけを列挙し、subagent の transcript (`<sid>/subagents/` 配下) は読まない。2 度読むのは、当たったファイルの末尾 (model / effort のための 64〜256KB) だけ
- 走査中の event loop の最大の空きは、5〜90 日で 22ms 以下、365 日で 60〜78ms。365 日の範囲には 19MB の 1 行がある

## 実用的な示唆

- 期間の中を全部探しても、60 日で数秒、365 日で 20 秒弱に収まる。読む量の固定の上限で止める必要はなく、時間の区切りで応答を分けて続きを引けば、進み具合を見せながら最後まで探せる
- 区切りは時間で決める。行の形で速さが 2 倍近く違う (当たる語・当たらない語・大小区別の有無) ため、バイトの区切りでは 1 回の応答にかかる時間が揃わない
- 大小区別なしの prefilter を、小文字化した文字列の `includes` から大小を畳む正規表現の `test` に替えると、走査の CPU の大半が消える見込み

## 検証の詳細

### 条件

- 機械: Apple M1 Max (10 コア)、メモリ 64GB
- 対象: この機械の 3 つの config dir の `projects/*/*.jsonl` (読むだけ)
- 方法: `packages/daemon/src/session-search.ts` の写しで、1 回の読む量の上限 (256MB) と当たりの件数の上限 (50) だけを外し、`sessionSearch` を小さいスクリプトから直接呼んだ。隔離 daemon も本番 daemon も使っていない
- 検索の語: 当たる語は英単語 1 語と日本語 1 語、当たらない語はでたらめな 10 文字、一覧は語なし。いずれも大小区別なし (既定) で、user / agent の両方を対象
- event loop の空き: 同じプロセスで `setTimeout(0)` を繰り返し、間隔の最大を取った

### 期間ごとの量と、256MB で読める割合

| 期間 | ファイル | 合計 | 256MB で読める割合 |
|---|---|---|---|
| 5 日 | 85 | 403MB | 63% |
| 30 日 | 219 | 932MB | 27% |
| 60 日 | 344 | 1,262MB | 20% |
| 90 日 | 492 | 1,555MB | 16% |
| 365 日 | 3,874 | 4,980MB | 5% |

候補の列挙 (ディレクトリの読みと stat) は 365 日でも 75〜150ms。

### 上限を外して全部探した時間

| 期間 | 当たらない語 | 当たる語 (英) | 当たる語 (日) | 語なし |
|---|---|---|---|---|
| 5 日 | 1.08 秒 / 403MB 読む | 1.10 秒 / 334MB / 38 件 | 0.85 秒 / 295MB / 38 件 | 0.28 秒 / 211MB |
| 30 日 | 2.25 秒 / 932MB | 2.24 秒 / 684MB / 84 件 | 1.73 秒 / 652MB / 92 件 | 0.58 秒 / 474MB |
| 60 日 | 3.21 秒 / 1,262MB | 3.10 秒 / 896MB / 132 件 | 2.48 秒 / 852MB / 140 件 | 0.85 秒 / 673MB |
| 90 日 | 4.01 秒 / 1,555MB | 3.93 秒 / 1,139MB / 191 件 | 3.13 秒 / 1,086MB / 211 件 | 1.13 秒 / 908MB |
| 365 日 | 17.52 秒 / 4,980MB | 18.73 秒 / 4,112MB / 1,145 件 | 15.82 秒 / 3,918MB / 1,286 件 | 6.71 秒 / 3,197MB |

当たる語の検索は、1 ファイルで要約 3 件が揃うとそのファイルの残りを読まないので、読む量は全体より少ない。それでも当たらない語と時間が変わらない。prefilter を通った行の JSON の parse が増えるためと見ているが、内訳は測っていない。

event loop の最大の空き: 5〜90 日は 6.7〜21.8ms、365 日は 59〜78ms。

### 1 回目と 2 回目

365 日の当たらない語を続けて 2 回: 18.74 秒 / 18.42 秒。差は測り方の揺れの内。OS の file cache を空にする手段 (purge は root が要る) が無いので、ファイルが cache に無い状態の速さは測れていない。この機械のメモリ (64GB) に対して 5GB は cache に載りうる。

### prefilter の大小区別

60 日の範囲の全行 (約 1,260M 文字) に対し、当たらない語で:

| 方法 | 時間 | 速さ |
|---|---|---|
| `line.toLowerCase().replaceAll("ſ", "s").includes(needle)` (今の大小区別なし) | 2.23 秒 | 494 Mchar/秒 |
| `new RegExp(needle, "iu").test(line)` | 0.25 秒 | 4,443 Mchar/秒 |
| `new RegExp(needle, "i").test(line)` | 0.19 秒 | 5,696 Mchar/秒 |
| `line.includes(needle)` (大小区別あり) | 0.16 秒 | 6,982 Mchar/秒 |

当たる語 (55,033 行が通る) でも `toLowerCase` 2.27 秒、`iu` 0.29 秒。

走査全体を大小区別ありで: 60 日 1.24 秒 (大小区別なしは 2.97 秒)、365 日 8.06 秒 (同 17.52 秒)。event loop の最大の空きも 365 日で 32ms に下がった。

### 先頭の情報の位置 (365 日、3,874 ファイル)

| 項目 | ファイル数 |
|---|---|
| 絶対パスの cwd が無い | 344 |
| 最初の cwd が 64KB より後 | 59 |
| `custom-title` の行がある | 621 |
| 最初の `custom-title` が 64KB より後 | 76 |
| 最初の `custom-title` が 4MB より後 | 12 |

語の無い検索の最初の読みを 4MB より小さくすると、title を拾うファイルが減る (title は cwd と開始時刻が揃うまでに読んだ範囲で拾っている)。

### 1 行の大きさ

365 日の範囲の約 198 万行のうち、1MB を超える行は 174、4MB を超える行は 12、最大は 19.2MB。走査は 1 行を処理するごとに経過を確かめて譲るので、19MB の行を処理する間は譲れない。365 日で event loop の空きが 60ms を超えたのはこの行のためと見ているが、行ごとの所要は測っていない。
