# Session Search が期間の中をどこまで読めるか (2026-11-24)

## 判明した事実

- 1 回の検索で読む量の上限 256MB では、既定の 5 日でも期間の中の transcript を読み切れなかった (5 日 63%、30 日 27%、60 日 20%、365 日 5%)
- 期間の中を全部読む速さは、大文字小文字を区別するかで 2 倍以上違う。区別しない側は prefilter が行ごとに `toLowerCase()` した文字列を作り、これが CPU の大半を占める。1 回目と 2 回目で速さは変わらず、律速は CPU
- 上限を外した daemon (時間の上限つき) で、当たらない語を探した時の届き方:

| 期間 | timeout | 区別する | 区別しない |
|---|---|---|---|
| 5 日 (83 ファイル) | 3000ms | 全部 0.6 秒 | 全部 0.9 秒 |
| 60 日 (344 ファイル) | 3000ms | 全部 1.3 秒 | 全部 3.0 秒 |
| 365 日 (3,874 ファイル) | 3000ms | 1,369 ファイル、146 日前まで | 352 ファイル、62 日前まで |
| 365 日 | 15000ms | 全部 8.8 秒 | 3,631 ファイル、309 日前まで (15.7 秒) |

- 当たる語は 50 件の上限で早く止まる: 365 日・区別する・英単語 1 語で 128 ファイル (13 日前まで) を 0.9 秒、語なしで 50 ファイルを 0.2 秒。応答は 74KB / 39KB
- timeout で止まる時、読みかけのファイルを読み終えるぶん上限を超える。365 日・区別しない・15000ms で 15.7 秒
- 走査中、別の接続の ping は中央値 0.3〜4.1ms、最大 5〜13ms (365 日・15000ms では最大 24ms (区別する) / 51ms (区別しない))。365 日の範囲には 19MB の 1 行があり、行の途中では譲れない
- 走査は `projects/<project>/*.jsonl` だけを列挙し、subagent の transcript (`<sid>/subagents/` 配下) は読まない。2 度読むのは、当たったファイルの末尾 (model / effort のための 64〜256KB) だけ
- 語の無い検索は各ファイルの先頭で止まるが、最初の読みが 4MB 単位なので 1 ファイル最大 4MB 読む

## 入れなかったもの

- 区別しない側の prefilter を大小を畳む正規表現 (`iu`) に替える高速化。区別しない側は 365 日の全部読みが約 17.5 秒 → 約 8.0 秒になる見込みだったが、フォームの既定を区別する側にしたので、区別しない側の速さには手を入れない (kawaz 2026-11-24)
- 複数ファイルを並べて読むこと。4 本で 365 日の全部読みが 5.3 秒 → 4.2 秒だったが、並べた本数だけ他の処理の待ちが延びる (DR-0029)

## 実用的な示唆

- 量の上限で止めると、期間を広げても古い方に届かず、どこまで探したかも言えない。時間で止めて、どこまで読んだか (ファイルの数と一番古い更新時刻) を返せば、人が範囲や時間を選び直せる
- 区別しない照合の前処理に、行ごとに小文字化した写しを作ると、それだけで走査が 2 倍以上遅くなる

## 検証の詳細

### 条件

- 機械: Apple M1 Max (10 コア)、メモリ 64GB
- 対象: この機械の 3 つの config dir の `projects/*/*.jsonl` (読むだけ)
- 方法 (上限を外した時の速さ): `packages/daemon/src/session-search.ts` の写しで、1 回の読む量の上限 (256MB) と当たりの件数の上限 (50) だけを外し、`sessionSearch` を小さいスクリプトから直接呼んだ。本番 daemon は使っていない
- 方法 (時間の上限つきの daemon): 隔離 daemon の HOME を一時ディレクトリにし、その下の `.claude-*` に本物の config dir の `projects/` への symlink だけを置いた (読むだけ。transcript は写していない)。socket で `session_search` を送り、同時に同じ接続と別の接続から 10ms 間隔で ping を送って往復の時間を取った
- 検索の語: 当たる語は英単語 1 語と日本語 1 語、当たらない語はでたらめな 10 文字、一覧は語なし。いずれも大小区別なし (既定) で、user / agent の両方を対象
- event loop の空き: 同じプロセスで `setTimeout(0)` を繰り返し、間隔の最大を取った

event loop の最大の空き: 5〜90 日は 6.7〜21.8ms、365 日は 59〜78ms。

### 1 回目と 2 回目

365 日の当たらない語を続けて 2 回: 18.74 秒 / 18.42 秒。差は測り方の揺れの内。OS の file cache を空にする手段 (purge は root が要る) が無いので、ファイルが cache に無い状態の速さは測れていない。この機械のメモリ (64GB) に対して 5GB は cache に載りうる。

### prefilter の大小区別

60 日の範囲の全行 (約 1,260M 文字) に対し、当たらない語で:

| 方法 | 時間 | 速さ |
|---|---|---|
| `line.toLowerCase().replaceAll("ſ", "s").includes(needle)` (今の大小区別なし) | 2.23 秒 | 494 Mchar/秒 |
| `new RegExp(needle, "iu").test(line)` | 0.25 秒 | 4,443 Mchar/秒 |
| `new RegExp(needle, "i").test(line)` | 0.19 秒 | 5,696 Mchar/秒 |
| `line.includes(needle)` (大小区別あり) | 0.16 秒 | 6,982 Mchar/秒 |

当たる語 (55,033 行が通る) でも `toLowerCase` 2.27 秒、`iu` 0.29 秒。

走査全体を大小区別ありで: 60 日 1.24 秒 (大小区別なしは 2.97 秒)、365 日 8.06 秒 (同 17.52 秒)。event loop の最大の空きも 365 日で 32ms に下がった。

### 1 行の大きさ

### 入れなかった高速化の実測

次の変更を試して測ったが、入れなかった (kawaz 2026-11-24。フォームの既定を区別する側にし、区別しない側の速さには手を入れない): 大文字小文字を区別しない prefilter を `toLowerCase` + `includes` から大小を畳む正規表現 (`iu`) に替える、cwd と開始時刻が分かった後は `custom-title` を含む行だけを head の parse に回す、長い 1 行の decode・strict の parse・head の parse の間でも event loop に譲る。並べて読むことも入れなかった。数字は測った事実として残す。

#### 高速化の後 (写しから直接呼ぶ、上限なし)

| 期間 | 当たらない語 | 当たる語 (英) | 当たる語 (日) | 語なし |

段ごとの効き (365 日、いずれも大文字小文字を区別しない検索):

| 段 | 当たらない語 | 当たる語 (英) | 語なし | event loop の最大の空き |

| 速くする前 | 17.5 秒 | 18.7 秒 | 6.7 秒 | 60〜78ms |
| prefilter を `iu` に | 8.0 秒 | 10.4〜10.5 秒 | 5.6〜5.8 秒 | 22〜30ms |
| 題の行だけを head の parse に | 5.1 秒 | 8.1 秒 | 3.4 秒 | 15〜29ms |

結果が同じであることの確認: 365 日で語なし・英単語・日本語・大小区別ありの英単語・大文字の英単語の 5 種を、替える前の写しと替えた後の写しで続けて引き、当たりの全欄 (順・抜粋・題・cwd・時刻) を JSON で比べて一致した。1 度、日本語の検索で一致しなかったのは、2 回の間に動いているセッションの transcript が書き足されたためで、引き直して一致した。

19MB の行の内訳 (当たる語の時): decode 約 6ms、strict の parse 約 14ms、head の parse 約 7ms。

#### 並べて読む

`scanCandidateFile` を N 本同時に走らせ、候補を順に配った (結果の組み立ては省いた):

| 本数 | 365 日・当たらない語 | 365 日・当たる語 (英) |
|---|---|---|
| 1 | 5.34 秒 | 7.68 秒 |
| 2 | 4.45 秒 | — |
| 4 | 4.19 秒 | 6.77 秒 |
| 8 | 4.01 秒 | — |

走査はそれぞれ 8ms ごとに譲るので、N 本並べると他の処理は最大で N × 8ms 待つ (DR-0029 追補が上限 2 本にしている理由と同じ)。
