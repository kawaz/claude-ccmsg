# daemon の Watch を削り、追いつきと push 起点の読みで fold を作る形 (DR-0045 の段階 2) を実機で確かめた

- Date: 2026-10-28
- 対象: Claude Code 2.1.312、ccmsg の作業コピー (v0.207.0 の上の段階 2、未 commit。下の不具合の修正の前と後)
- 動機: [DR-0045](../decisions/DR-0045-say-speaks-in-tool-shown-from-transcript.md) の段階 2 を本物の claude と webui で通して、次を見る
  - Status タブ (TODO / ctx)、サイドバーの API error、Sessions 一覧の並び (`last_user_input_at`) が、再読み込みなしで追従すること
  - daemon を起動し直した後、module の名乗り直しと追いつきで状態が戻り、続きも live で動くこと
  - daemon が transcript の jsonl を fs.watch / poll で追っていないこと
  - module の無いセッションには live の更新が無く、one-shot の `session_status` はファイルの 1 回の読みで答えること
- 方法:
  - daemon: 自分用 workspace の `packages/daemon/src/index.ts --foreground` を起動した。`CCMSG_STATE_DIR` / `CCMSG_CONFIG_DIR` / `CCMSG_DATA_DIR` / `HOME` は一時ディレクトリに向け、`CCMSG_CLAUDE_CONFIG_DIRS` には試験用の config home だけを名指した (verify skill の手順)
  - 試験用の config home: `settings.json` は普段の設定から `apiKeyHelper` と `env` の `ANTHROPIC_*` を抜いたもの。`.claude.json` に onboarding 済み・ダミー鍵の承認・作業ディレクトリの trust を置いた
  - 試験セッション: tmux の中で `env -i` から起動した (`--model sonnet --permission-mode default --debug`、`CLAUDE_CODE_MAX_RETRIES=0`、daemon と同じ `CCMSG_*`)
    - `--plugin-dir <自分用 workspace>` を付けた `🤖ccmsg-verify-stage2`。並びの確認と再現のために、同じ形の `🤖ccmsg-verify-stage2-b` / `🤖ccmsg-verify-stage2-c` も立てた
    - 付けない `🤖ccmsg-verify-stage2-nomod`
    - model の応答は Messages API の代役 (reference `claude-mods/lab-setup`) が返した。prompt の最後の行の印で、TaskCreate / TaskUpdate の tool_use、HTTP 500 の api_error、普通の文を返し分け、main の request ごとに `usage.input_tokens` を 7000 ずつ増やした
    - このモデル名では TaskCreate / TaskUpdate が出ない (Claude Code が todo の tool を古いモデル名か `CLAUDE_CODE_ENABLE_TODO_TOOLS` でだけ有効にする)。起動の env に `CLAUDE_CODE_ENABLE_TASKS=1` と `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` を足した
  - webui: daemon の HTTP を `playwright-cli` の名前付きセッションで開き、Status タブとサイドバーを snapshot で見た
  - 観測:
    - user role で daemon の socket に繋ぐ小さなスクリプトで、`session_status_subscribe` の push (`ev:"session_status"`) を時刻付きで記録し、one-shot の `session_status` / `session_errors` / `peers` を引いた
    - daemon の `trace.jsonl` の `transcript_read` (`source`) と daemon.log
    - 対照: 段階 2 の前の commit を一時ディレクトリに切り出した workspace の daemon を、同じ state dir・同じ試験セッションで起動し、Status を購読した状態にした
  - 修正の確認: 下の不具合を直した作業コピーで、daemon を先に起動し、その後に module のあるセッション `🤖ccmsg-verify-stage2-fix` を新しく起動した。prompt を打つ前に `session_status` が `session has no transcript` で断ることを見てから最初の prompt を打ち、Status タブを開いたまま TaskCreate → TaskUpdate (`in_progress`) → TaskUpdate (`completed`) の turn を進めた

## 判明した事実

| 確かめたこと | 期待 | 実際 | 根拠の観測 |
|---|---|---|---|
| (a) Status の ctx | turn の進行で再読み込みなしに更新 | 更新された (3% → 5%、4% → 6% 等) | webui の snapshot。ただし ctx は module の facts (session.measure) の push でも動くので、fold の経路の証拠にはならない |
| (a) Status の TODO (daemon の起動の後に始まったセッション、修正前) | TaskCreate / TaskUpdate の結果の行で更新 | **更新されなかった**。TaskCreate の後、開いたままのタブは「background / TODO はまだありません」のまま。新しいタブで開くと `TODO (1)` が出た | 購読の push は、結果の行を読んだ後に 1 本も来なかった。one-shot の `session_status` は正しい TODO を返した。2 つのセッションで再現 (下の「直した不具合」) |
| (a) Status の TODO (daemon の起動の後に始まったセッション、修正後) | 同上 | 更新された。開いたままのタブで `TODO (1)` → `⟳ #1` (`in_progress`) → `completed (1)` と、再読み込みなしに進んだ | 3 つの turn とも、結果の行の `transcript_read` (`retry`) の 1 ms 後に、その結果を載せた push が来た (`pending` / `in_progress` / `completed`) |

| (b) API error | サイドバーのエラー表示に出て、次の正常な応答で消える | 出た (`Error (1)`、`server_error`)。正常な応答の後に消えた | webui の snapshot と one-shot の `session_errors` |
| (c) 最後のユーザ入力 | prompt のたびに `last_user_input_at` が進み、並びが変わる | 進んだ。並び「prompt」の Sessions 一覧で、prompt を打ったセッションが再読み込みなしに先頭へ移った (`-b` に打つと `-b` が先頭、続けて `🤖ccmsg-verify-stage2` に打つとそれが先頭) | webui の snapshot と one-shot の `peers` |
| (d) daemon の再起動 | module の名乗り直しの後、TODO / ctx / `last_user_input_at` が追いつきで戻る | 名乗り直しは起動の約 4 秒後。webui を開き直すと TODO (`in_progress`)・ctx・並びが再起動の前と同じに戻った | one-shot と webui の snapshot |
| (d) 再起動の直後の turn | 続きも live で更新 | Status の TODO が push で更新され、Timeline にも行が live で出た | 購読の push と webui の snapshot |
| (e) fs.watch の監視が無い (lsof) | 段階 2 の daemon に KQUEUE / FSEvents の fd が無い | 段階 2 も前の daemon も同じ: KQUEUE が 3 つ、jsonl の fd 無し、FSEvents の fd 無し。lsof では差が出ない | `lsof -p`。前の daemon の Watch は jsonl のディレクトリを `fs.watch` するので、FSEvents (fd を持たない) になる。両方に FSEvents の thread (`CFThreadLoop`) があり、これは両方が持つ agents の poller の `sessions/` の `fs.watch` でも説明できる (`sample` の thread 一覧) |
| (e) fs.watch の監視が無い (代わりの観測) | 段階 2 の daemon は jsonl を自分で追わない | 段階 2: `transcript_read` の `source` は `push` 20 回 / `retry` 21 回だけ、daemon.log に `transcript tail` の行が無い。前の daemon: 起動で 4 セッション分の `transcript tail: create`、読みに `source: poll` / `fs_watch` (module の無いセッションの分も) | trace.jsonl と daemon.log |

### 直した不具合: transcript の無いうちに live になったセッションの Status の fold が動かなかった

- 起きた場面: daemon の起動の後に、module のあるセッションを新しく起動した時。最初の prompt の前は hello が transcript を名乗らない (`session_status` が `session has no transcript` で断る)。最初の prompt で jsonl ができた後も、Status タブの TODO が live で更新されなかった
- 修正前の観測:
  - 結果の行 (`toolUseResult` 付き) を relay が読んだ後、購読の push が来なかった。来る push は module の facts の変化 (turn の状態、session.measure の ctx) の時だけで、その時点で書かれていた行までの TODO を載せた
  - one-shot の `session_status` は正しい TODO を返した。同じファイルを daemon の `createSessionStatusState` + `foldLine` に通しても TODO は正しく変わった (fold の関数そのものは正しい)
  - daemon を起動し直すと (module は transcript を名乗った状態で名乗り直す)、同じセッションで push が来た
  - 同じセッションの `last_user_input_at` と API error は追従していた
- 原因: live になった時の `startCatchUp` は `relay.file` が無いので、各 fold の `restart(undefined)` を呼ぶ。Status の fold (`sessionStatusFold`) はそこで状態を持たなくなり、`take` も `settle` も何もしなかった。API error と最後のユーザ入力の fold は `restart` でファイルを見ないので動いていた。`relayPushed` は最初の push で `relay.file` を埋めるが、fold の追いつきをやり直していなかった
- 修正: `relayPushed` が最初の push で `relay.file` を埋めた時、live のセッションなら fold の追いつきをやり直す (`startCatchUp`)
- 修正後の観測: 上の表の (a) の「修正後」の行。daemon の起動の後に始めたセッションで、TODO が 3 つの turn とも結果の行の読みの 1 ms 後の push で更新された。修正前のセッションでは最初の prompt の前 (起動の数秒後) に `gave up waiting ... rows=5` が出ていたが、修正後のセッションでは出なかった (修正前に出た理由と、修正後に出ない理由は確かめていない)

### その他の観測

- `transcript relay: gave up waiting ... rows=1 after 5000ms` は、TaskCreate / TaskUpdate を呼んだ turn のたびに 1 回出る (修正後のセッションで 3 turn とも。prompt に文で答えるだけの turn では出ない)
  - その turn では、試験セッションの debug log の `session.append` が 8 回なのに、jsonl の uuid を持つ行は 7 行だった (文で答えるだけの最初の turn は、起動の分を含めて 16 回 / 16 行で一致)
  - 多い 1 回は、tool_result の append (jsonl の tool_result の行の 3 ms 後) と `total_tokens_reminder` の append の間に来ていた。jsonl に対応する行が無いので、relay はその uuid を 5 秒待って諦めている
  - その append が何の行か (type) は未特定。debug log には append の中身が出ず、trace.jsonl にも push の uuid は残らない
  - 行は抜けていない (読みはファイルの byte offset で続くので、その後の行は次の読みで来る)。この turn ごとに、5 秒の間 50 ms 間隔の読み直しが続く
- 普段の設定は、別の版の ccmsg の marketplace を置き場のまま読む宣言を持つ。そのため module の無いセッションにも、その plugin の classic hook (`ccmsg hello --hook`) が載り、SessionStart で失敗した (試験用の config home に plugin が install されていないため)。daemon に hello は届かず、module の無いセッションは `no_module` のままだった

## 未検証

- lsof に代わる、プロセスの外から fs.watch の有無を直接見る手段 (FSEvents の stream の数)。`lsmp` は root が無いと他のプロセスを見られない
- `gave up waiting` で待っていた行の type。TaskCreate / TaskUpdate 以外の tool (Bash 等) の turn でも出るか
- subagent / teammate の行 (`agentId` 付き) の fold への流れ
- compaction の後の同じ uuid の push の重複除去
- 追いつきの最中に push が来る場面 (追いつきは数 ms で終わり、重ならなかった)
- hello の cwd / repo_root が変わった時の追いつき直し
