## 判明した事実

- **§3.4 (廃止したものへの言及) が圧倒的に多い**: 全 61 件のうち 34 件。特に「追補」を本文の後ろに
  積む書き方 (DR-0002 §4/§5、DR-0003 Addendum、DR-0004 末尾 blockquote) が、旧規定と新規定を同じ
  文書に併存させ、読み手に旧案の否定を読ませていた。DR-0004 は追補 blockquote (124 行) が
  Decision 本体 (63 行) の 2 倍で、§3.5 (分量) にも同時に当たる
- **コードコメントは `kawaz rNN mMM` 形式の会話参照が 30 件**。room 番号だけで辿れず、根拠は
  同じコメント内に既に書かれていることが多い (= 参照を消しても情報は減らない)
- **§2.4 (曖昧な数値) は「値はあるが根拠がない」形が主**: `[保留] T は実装時に調整` (60 秒で実装済み)、
  `10MB 目安`、`25ms → 3000ms 計 12 回`、`3 min default`。根拠なしの値は実装者が調整できない
- **§3.1 通読で見つかった文書間矛盾** (kawaz 裁定要、下記): DR-0002 §4「後方互換は原則実装しない」
  vs DR-0016 §2.3「`since` (mid) は旧 client 互換のため残す」vs DR-0032「version の違う daemon 同士が
  同じ契約で話す」。DR-0004 §5 fragment locator vs `webui-url-grammar.md`「hash は使わない」
- **規範に最も適合していたのは `webui-url-grammar.md`** (指摘 0 件): 目的が結果の性質で書かれ
  (§1.1)、載せないものが理由付きで境界として書かれ (§2.2/§2.5)、固定すべき所 (予約キー小文字 /
  params 大文字) と任せる所の区別がある (§2.3)
- **DR-0004 §4「webui のための protocol 拡張はしない」は §1.4 の「増やさない」宣言だが、その後
  数十の webui 専用 op が追加されており、§2.7 (壊す変更を検出するテスト) が無かったため文章だけでは
  止まらなかった実例**。規範 §2.7 の主張を裏付ける

## 規範そのものへのフィードバック

- **DR (判断記録) と仕様の区別が規範に無い**。§3.4「廃止したものへの言及を消す」を DR に適用すると、
  Accepted 時点の決定文を後から書き換えることになる。本リポの DR は「Superseded by」注記 + 追補で
  運用されていて、規範の想定 (現行仕様を 1 文書で保つ) と合わない。規範側で「DR は不変、現行仕様は
  design/ に置く」か「DR も現行化する」かを決めないと、§3.4 の適用範囲が人によって割れる。
  本監査は「DR も現行化する (Status/Superseded 注記は残す)」で進めた
- **§3.4 と attribution の衝突**: DR-0001 の記述規約 ([kawaz] / [提案] + 一次資料参照) は決定の出所を
  残すためのもので、`kawaz 2026-07-12 裁定` のような日付付き attribution は正当。一方 `kawaz r26 mid=103`
  は room 番号だけで辿れない。規範に「参照は辿れる形 (一次資料 path / DR 節 / issue file) で書く。
  会話 id は辿れないので書かない」の一行があると、no-historical-noise の `kawaz rNN mMM` 禁止と一貫する
- **§2.4 は「値がない」ケースしか例示していない**。実際に多かったのは「値はあるが根拠がない」
  (`3 min default`、`10MB 目安`)。根拠が無いと監査側が推定で埋めるしかなく (#5 参照)、それは
  規範が防ぎたい「実装に投げる」の別形。例に「値だけ書いて根拠を省く」を足すと良い
- **§3.3 の検証 script は他文書への参照 (`DR-0001 §9`、`一次資料 §3`) を自文書の節と混同する**。
  regex を「直前に `DR-NNNN` や `一次資料` が無い §」に絞る必要があり、そのままでは偽陽性が出る
