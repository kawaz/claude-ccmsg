# hooks module の登録・契約・`$` の受け渡し・import・test の約束を 2.1.309 で確かめる

- Date: 2026-10-25
- 対象: Claude Code 2.1.309 (`claude --version` の出力 `2.1.309 (Claude Code)`)
- 動機: rules リポの reference `claude-mods/` に findings の知見 (2026-10-15 の 2 本と 2026-10-23 の 1 本) を反映する前に、`claude plugin validate` / `claude plugin test` だけで決まる項目を手元の版で確かめ直す
- 方法: 一時ディレクトリに最小の plugin (`.claude-plugin/plugin.json` と、`hooks/hooks.json` が `{ "modules": ["./register.ts"] }` で `register.ts` を名指す形) を項目ごとに置き、`claude plugin validate <dir>` と、plugin のディレクトリで `claude plugin test .` を走らせた。`CLAUDE_CONFIG_DIR` と `TMPDIR` はその一時ディレクトリの中に向けた (ログインしていない config home)。API の応答は使っていない。対話セッションは起動していない
- 回数: 各項目 2 回 (同じ plugin で 2 回走らせ、出力は 2 回とも同じ)。出力の一時ディレクトリのパスは `<W>` に置き換えた
- 機械: macOS の managed settings の置き場 (`/Library/Application Support/ClaudeCode`) が無い機械

## 判明した事実

- matcher なしで同じ event を 2 回 `on()` すると validate がエラーにする (`on("session.start") is registered twice without a matcher; the first is at <file>:2`)
- matcher 付きなら重複は通る。matcher なし 1 本 + `{}` 2 本 + `session.*`、同じ matcher の `command.run` 2 本の組で validate はエラー無しで、6 本とも hooks に並ぶ
- `$.state` の key を `types/index.d.ts` の `PluginState` に宣言しないと、validate が `pstate.boot is not declared: the manifest's types contract must name it in interface PluginState { pstate: { boot: ... } }` でエラーにする
- 契約のファイルに top-level の `export {}` があると、契約として読まれない (`a contract exports types and nothing else`)。`export type` だけを持つ形と、export の無い形は通る
- `$` を配列の中の関数へ引数で渡すと validate がエラーにする (`$ itself is passed as an argument (bound, passed, spread, returned or read)`)。top-level に宣言した関数へ `$` を渡す形、`register` から top-level の関数に `on` を渡して登録させる形、hook の中の closure が `$` を閉じて使う形は通る
- hooks module から相対 import (`./helper`) した別ファイルの関数は、`claude plugin test` で engine の host に読ませた時に走る
- `$.session.start(...)` を呼ぶ test で、test の側が `session.start` に答えないと `HooksError: no implementation for session.start` で失敗する
- 同じ plugin の `session.start` に外側から A, B, D の順に登録し、B が `next(e)` の後に throw すると、記録は `A before, B before, D before, D after, B after` で、A の `await next(e)` の後は走らない (どの hook の `.catch` も `next(e)` を返す)
- `classic.Stop` / `skill.prompt` / `prompt.attachment` / `prompt.context` / `session.compact` を hook する plugin を validate しても、組織が管理する環境で飛ばされる hook の注記は、テキスト出力にも `--json` の `notes` / `advice` にも出ない (管理されていない機械で)

## 実用的な示唆 / ベストプラクティス

- 同じ event を関心ごとに分けて登録するなら matcher を付ける。ただし同じ plugin の中では、内側の hook の失敗が外側の hook の後の部分を止めるので、関心ごとの登録は互いの続きを守らない
- `$.state` を使う mod は `types/index.d.ts` に `PluginState` を書く。契約ファイルには型の export 以外を置かない
- `$` を受け取る処理は名前付きの top-level 関数にする
- validate の注記の有無から、組織が管理する機械で hook が飛ばされるかを判断しない (管理されていない機械では注記が出ない)

### `$` の受け渡し

`pdollar/hooks/register.ts` (配列の中の関数へ渡す):

```ts
const parts = [{ after: async ($: any) => { await $.ui.log('x', { to: 'debug' }) } }]
export function register(on: any): void {
  on('session.start', async ($: any, e: any, next: any) => {
    const r = await next(e)
    for (const p of parts) await p.after($)
    return r
  })
}
```

export function register(on: any): void {

### 失敗の伝わり方 (`claude plugin test`)

`pfail/hooks/register.ts`:

```ts
const order: string[] = []
export function register(on: any): void {
  on('session.start', {}, async ($: any, e: any, next: any) => {
    order.push('A before'); const r = await next(e); order.push('A after'); return r
  }).catch(($: any, e: any, next: any) => next(e))
  on('session.start', {}, async ($: any, e: any, next: any) => {
    order.push('B before'); await next(e); order.push('B after'); throw new Error('B fails')
  }).catch(($: any, e: any, next: any) => next(e))
  on('session.start', {}, async ($: any, e: any, next: any) => {
    order.push('D before'); const r = await next(e); order.push('D after'); return r
  }).catch(($: any, e: any, next: any) => next(e))
  on('command.run', { command: 'order' }, async () => ({ text: order.join(', ') }))
}
```

test は `session.start` に test の側で答え (`on('session.start', ($, e) => ({ cwd: e.cwd }))`)、`$.session.start(...)` の後に `$.command.run({ command: 'order', ... })` の `text` を読む (期待値をわざと外して、受け取った値を出力に出させた)。

```text
(fail) register > order [35.02ms]
  AssertionError: expect(received).toBe()
  
  Expected: "SHOW-ME"
  Received: "A before, B before, D before, D after, B after"
  
  the engine reported:
    hook failed closed: pfail: errorKind=Error errorChars=7 (session.start; its .catch answered)
    pfail's session.start hook was skipped: pfail: B fails
```

`next(e)` の前に throw する形はこの版では試していない (2.1.308 は findings 2026-10-23)。

### 組織が管理する環境の注記

`pclassic/hooks/register.ts` は `classic.Stop` / `skill.prompt` / `prompt.attachment` / `prompt.context` / `session.compact` / `tool.call` / `turn.step` (`async function*` で `return yield* next(e)`) / `session.start` を 1 本ずつ `next(e)` だけで hook する。validate の出力:

```text
  ❯ ./register.ts hooks: classic.Stop, skill.prompt, prompt.attachment, prompt.context, session.compact, tool.call, turn.step, session.start
  ❯ ./register.ts gating hook without .catch: classic.Stop
  ❯ ./register.ts gating hook without .catch: session.compact
  ❯ ./register.ts gating hook without .catch: tool.call
  ❯ ./register.ts calls: nothing on $
```

`--json` でも、`manifest.notes` と `advice` は空で、`contents[].notes` は上の 5 行だけだった。context-notify の DR-0003 は 2.1.299 で validate の注記の文面を記録している (「managed settings のある機械では、利用者が自分で入れた plugin の `classic.*` / `skill.prompt` hook は走らない」)。その違いが版によるのか機械によるのかは切り分けていない。
