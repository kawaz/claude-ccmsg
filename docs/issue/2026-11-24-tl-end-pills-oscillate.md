# TL の末尾で 2 つのピルが毎フレーム交互に出入りし続ける

## 観測

TL が末尾から 35px ほど以内に寄った位置で、末尾付近の項目の高さが伸びると、「↑最新のプロンプトへ移動↑」(`.tl-latest-prompt`) と「↓先頭に移動↓」(`.tl-bottom-pill`) が 1 フレームごとに交互に出入りし、止まらない (Chromium と WebKit の両方、隔離環境の e2e の中で採取)。

- 「最新=出る / 先頭=隠れる」と「最新=隠れる / 先頭=出る」が 1 フレームごとに反転する
- 行の列 (`.tl-lines`) の高さが 35px (Chromium) / 31px (WebKit) 往復する
- きっかけは末尾付近の項目が伸びること。btw の答えを md から source に切り替えた時と、答えに 14px の要素を足しただけの時の両方で起きた
- 末尾の要素が動き続けるので、playwright の click が「element is not stable」で 30 秒待って落ちる

## 原因の見立て (コードからの読み。実測での裏付けは未了)

`.tl-latest-prompt` は行の列の流れの中にある要素で、出ると行の列が伸びる。伸びると一番下の状態の行が表示領域から外れて「出す条件」が偽になり、隠れる。隠れると縮んで条件が真に戻る。出す条件 (`Timeline.tsx` の `latestPromptInView` / `bottomControlsInView` / `tailInView`) が、自分の出入りで変わる高さに依っている。

## 特定に要る観測

- 振動している間の、3 つの条件の値と行の列の高さ・scrollTop の時系列
- ピルを高さを持ったまま隠した時 (流れの高さが変わらない形) に振動が止まるか

## 実測 (2026-11-24)

隔離 daemon (e2e の harness) に長い TL (発言 2 つと 60 段落の答え 2 つ) を出し、幅 1200・高さ 900 の Chromium と WebKit で、最下部から wheel で d px 上げてから最後の項目に高さ 14px の要素を足し、1 フレームごとに 2 つのピルの hidden、3 つの条件 (見張る要素の矩形から求めた値)、行の列の高さ、scrollTop を採った。

- d = 10 / 20 / 30 (Chromium)、d = 10 (WebKit。wheel の 1 回で動く量が Chromium と違う) で、約 1 秒 (66 フレーム) の間に 59〜65 回入れ替わった。最下部から 8px ずつ wheel で上げ下げしただけでも (項目は伸ばさない)、両方のブラウザで同じ振動が起きた。項目が伸びることは要らず、状態の行の箱が表示領域の下端から浅く入る位置に来ることがきっかけ
- 振動の 1 周期 (Chromium、d = 20 の伸びた後): 「最新=出る / 先頭=隠れる」のフレームは行の列が 5008.6px で、箱の上端が表示領域の下端より 27.4px 下 (bottomControlsInView = 偽)。次の「最新=隠れる / 先頭=出る」のフレームは 4973.2px で、箱の上端が下端より 8px 上 (真)。scrollTop は 4169 のまま動かない。latestPromptInView はどのフレームも偽。tailInView は、縮んだ時に scrollTop が上限に切り詰められる周期 (伸ばす前の d = 20) では一緒に入れ替わり、伸びた後の周期では偽のまま
- 高さの往復は Chromium 35.4px、WebKit 31.4px。ボタンの高さ (30.6px / 26.6px、margin 0) と行の列の gap (4.8px) の和に一致する
- 隠したボタンが高さを持ったままになる CSS (`display: block; visibility: hidden`) を足すと、同じ手順で入れ替わりは 0〜1 回 (wheel の上げ下げでは 2 回) で止まった

## 原因

1. 2 つのピルが毎フレーム入れ替わるのは、状態の行の箱 (`.tl-bottom-controls`) の見え方 (`bottomControlsInView`) が毎フレーム反転するから。「↑最新のプロンプトへ移動↑」はこれが真の時だけ出て、「↓先頭に移動↓」はこれが真の間は出ないので、2 つが逆向きに入れ替わる。最新のプロンプトの見え方は振動の間ずっと偽
2. 箱の見え方が反転するのは、ボタンが行の列の中、箱の上にあり、出ると箱を自分の分 (35.4px / 31.4px) だけ下へ押すから。箱が表示領域の下端からその分より浅く入っている所では、出ると箱が外れ、消えると戻る。読み手が wheel で動かした後は末尾追従をやめているので scrollTop は動かず、押した分がそのまま箱の位置に出る
3. 出す条件が、ボタン自身の出入りで変わる量 (ボタンを含めた並びでの箱の位置) に依っていた。高さを残して隠すと止まることがこれを裏付ける

## 直した内容

- 「↑最新のプロンプトへ移動↑」を行の列の流れから外して浮かせた (kawaz 2026-11-24)。`position: absolute` で行の列 (`position: relative`) を基準にし、末尾の余白の上端から行の間の gap だけ下 (流れの中に置いていた時と同じ、手前に描かれている行の下端から gap 下) に置く。横は行の列の内側の右端のまま。出ても隠れても行の列の高さと状態の行の箱の位置が変わらないので、原因の 2 段目の押し出しが無くなる。出す条件 (DR-0054 §10 / §11) と JS は変えていない
- 「↓先頭に移動↓」は高さ 0 の sticky な台の中の `position: absolute` で、もともと流れに高さを持たない。wheel の上げ下げでこのボタンが出入りしても、行の列の高さ・scrollHeight は 1 つの値のままだった (Chromium 4959.2px / 4993、WebKit 4947.2px / 4981) ので触っていない
- 直した後、同じ手順で両方のブラウザ・全ての d で入れ替わりは d = 10 の 1 回 (伸びた 14px で箱が外れ、最新から先頭へ 1 度だけ替わる) と 0 回、wheel の上げ下げは上げと下げの 2 回だけ、2 つが同時に出たフレームは 0。行の列の高さはどの入れ替わりの前後でも同じで、伸びた 14px の分だけ変わる
- 浮いたボタンは、末尾の経過時間・今日の帯・応答中の行・Waiting の行のどれが最後でも、その下に描かれる。末尾の余白の中の状態の行 (context の行・リポジトリの行) と右下の FAB とは重ならない (幅 390 と 1280、Chromium と WebKit、最下部と 10・30px 上のスクリーンショットと矩形の交差で確認)
- 縦の位置を CSS anchor positioning で付ける形は、行の列の行に効く selector が重く採らなかった (1007 行の TL で、全ての行に `anchor-name` を付けると Chromium の layout が 1 回約 100ms から約 1770ms、ボタンの手前の 2 つに絞っても行を 1 つ足す時の WebKit の再計算が約 3ms から約 40ms)。末尾の余白の上端から置く形では、同じ TL の layout は Chromium 約 96ms・WebKit 約 42ms (浮かせない時は約 95〜101ms・約 45〜49ms)、行を 1 つ足す時の再計算は Chromium 約 92〜94ms・WebKit 約 4ms (浮かせない時は約 93〜94ms・約 3ms) だった
- 試験: `packages/webui/test/timeline-end-pills-settle.dom.test.ts` (箱の位置を -45〜45px で上下に動かし、各位置で答えが 1 つに決まり次のフレームで変わらず、2 つが同時に出ない)、`packages/webui/e2e/end-pills-settle.e2e.ts` (出ても隠れても行の列の高さ・scrollHeight・状態の行の箱の位置が同じこと、最下部から 10 / 20 / 30px 上で最後の項目を伸ばし、5 フレーム以内に落ち着いて 2 つが同時に出ず、行の列の高さが動かないこと)。e2e は流れの中に置いていた時のコードで落ちることを確かめた
