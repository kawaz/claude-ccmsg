# agy (Antigravity の CLI) を ccmsg の tool から会話として使う

## 目的

Claude Code のセッションから、agy (Google の Antigravity の CLI。Gemini と、同じ口から Claude 等を呼べる) の会話を、チームメートや worker のように使えるようにする。初回で会話の ID を受け取り、2 回目以降はその ID を渡して同じ会話に依頼を足す。

Bash から `agy -p` を直接呼ぶ形は、auto mode の classifier に引数の違うたびに止められる (全許可やシェルを使わせる依頼が、ユーザの許可の後でも止められ続けた)。MCP の tool にすれば、tool 名の完全一致 allow 1 つで済む。

## kawaz の仕様案

```
agy {
  op:
    | "run"     agyid が無ければ新規、あれば既存の会話への依頼。プロセスが生きていなければ起動する。
                どの場合も tool の利用側からは違いが見えない
    | "status"  生きているか、ターン中か
    | "abort"
  agyid?:   新規の時は付けない
  prompt,
  cwd:      新規の時だけ付ける (無ければプロジェクトのディレクトリ)
  dirs:     新規の時だけ付ける (無ければプロジェクトのディレクトリ)
    [ { path, containerpath?, write: bool }, … ]
}
```

tool の裏では agy を spawn し、stream-json (`--input-format stream-json --output-format stream-json`) で ccmsg が入出力する。

## 議論で決まったこと (2026-11-25、kawaz)

- run は非同期。agyid はすぐ返し、応答は後で知らせとして届ける
- 新規の時に model と effort は必須
- 権限は全許可 (`--dangerously-skip-permissions`)。書ける範囲はコンテナで囲う前提。最初はホスト上で動かし、コンテナで動かす実験を並行して進め、使えそうになったら切り替える
- model を run ごとに替えるのは cache が効かなくなるのでやらない
- agyid は起動したセッション以外も使ってよい (セッションの引き継ぎで agy の会話も引き継げる)
- 何もしていないプロセスを雑に殺さない (重い依頼は 20 分かけて仕事をすることがあり、出力が止まっていても agy の中で裏の処理を待っているだけのことがある)
- status と run の結果は、詳しさを引数で選べるようにする。最低限 (生きているか、ターン中か、最後の応答、エラー) と、詳細 (起動時のモデル・effort・cwd・dirs、usage の累計、cache の利用状況、拒否された道具、利用枠の戻り時間) 。引き継いだ agyid でも中身が分かるようにする
- 中断は、Claude Code の「中断してすぐ次のプロンプト」と同じことができるかを agy の仕様で確かめてから決める (下の実測で確かめた)

## agy の実測 (1.5.15、macOS、2026-11-25)

詳細と再現手順は claude-rules-personal の reference の `agy/` (`headless.md`・`permissions.md`・`agents.md`)。tool の仕様に効く点:

- 会話の ID は agy が発行する。自分で作った uuid を `--conversation` に渡すと `not found` で別の新しい会話になる。stream-json では起動から約 4 秒で出る `init` に `conversation_id` が入るので、応答を待たずに agyid を返せる
- 終わったプロセスの会話は、`--input-format stream-json --output-format stream-json --conversation <ID>` で同じ ID のまま再開でき、前の内容を覚えている。再開時に `--model` を替えても同じ会話として続く
- ターン中に標準入力へ次の依頼を書いても、agy が今のターンを終えてから順に処理した (ccmsg 側で順番待ちを持たなくてよい)
- 今のターンだけを止めてプロセスを生かす口は無い (`control_request` はエラーで終わる)。本体に SIGINT か SIGTERM を送ると、すぐに `"finished_reason":"interrupted"` の `result` を出してプロセスが終わる。止めた会話は `--conversation` で再開でき、壊れていない。abort は「信号で止める → 次の run で再開して流し込む」で実現できる
- `agy` はラッパのシェルスクリプトで、本体 `antigravity` を exec する。信号は本体の PID に送る
- 同じ会話を 2 つのプロセスで同時に開くと、片方の書き込みが失われる (閉じた後に開き直すと、片方の分しか残っていなかった)。1 つの agyid は 1 つのプロセスだけが開くように ccmsg 側で縛る
- 「ターン中か」は「依頼を書いてから、その回の `result` がまだ来ていない」で判定できる (agy の中で裏の処理を待っている間もターン中になる)
- cache: `usage.cache_read_tokens` は出るが、cache に書いた分と TTL は出ない。TTL を選ぶ設定も無い。agy 経由の Claude Sonnet で、会話の cache は 5 分前後で切れた (3 分半後は効き、6 分半後は外れた)。プロセスを生かしても延びない。status の詳細に「最後のターンからの経過時間」があると、呼ぶ側が判断できる
- 全許可でない時は、シェル・`run_workflow` が拒否され、`invoke_subagent` の結果を待たずに回が終わる。全許可ならどれも動く
- `--sandbox` は全許可と併せると何も縛らない (作業ディレクトリの外への書き込み、ネットワークが通った)。ホスト上で `write: false` を守らせる手段は agy の側に無い
- 利用枠 (個人のアカウント) は Gemini のモデル全体で 1 つ。尽きると `AGY_ERROR` に `"error_code":429` と戻るまでの時間が出て、終了コード 3。agy 経由の Claude のモデルは別に数えられ、Gemini が尽きた時も通った
- 結果の `result` に `status`・`response`・`usage`・`denied_actions`・`finished_reason` が入る。知らせに載せる材料になる

## 決まっていない点

- dirs の `write: false` と `containerpath` は、コンテナで動かす時だけ効く。Linux 版の agy がコンテナで動くか、ログインの資格情報をどう渡すかは未確認
- 何もしていないプロセスをいつ終わらせるか (殺さずに残す方針。数やメモリの上限を設けるか)
- 新規の時の任意の項目に `--agent` (agy の agent 定義でシステムプロンプトと道具を決める) と `--json-schema` (応答の形を決める) を入れるか
- Gemini のモデルの cache の寿命 (未測定)
